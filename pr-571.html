Architecture Overview

CI/CD YAML manifests → sync_policies reconciler → IAM DB (PolicyBundle immutable content + PolicyAssignment binding rows) → five policy planes, each routed to its own enforcement owner. LLM operational policy is the one plane that enters the IAM validate_api_key() immutable snapshot (INV-057-7 no re-resolve); deployment/runtime/egress/sidecar/data planes are enforced at deployment-time or at the network/ingress/data boundaries.

Reading guide

Element Meaning
YAML → sync_policies → DB Policy-as-Code lifecycle. Manifests are desired state; DB is runtime source of truth (INV-191-5: no hot-path YAML reads).
Bundle ┄ Assignment Reusable content + binding relation. One PolicyBundle version may be assigned to many targets (INV-191-1/2 · solves PRD-132 §情境A fan-out).
Console → Assignment GitOps baseline is read-only in Console (INV-191-6); only audited overrides may mutate assignments.
Five planes Each plane has a distinct enforcement owner. LLM is the only plane that enters validate snapshot; the others enforce at container/network/ingress/data boundaries.
LLM ⇒ Validate ┄ Snap → GW Live path. Resolver order Deployment > Application > Group > Tenant. Deployment scope applies only when the request carries deployment identity (INV-191-4 · application-level key stops at Application).
⛔ Hard denies Cross-plane invariants enforced by the agentd network boundary regardless of any allowlist: metadata endpoint, docker socket, host network, privileged container (INV-191-7).
What this diagram replaces. The earlier operational ADR-185 stored scope_level/scope_id directly on RateLimitPolicy / GuardrailPolicy rows with an advisory four-level resolver that never connected to the live path. ADR-191 keeps policy content reusable, makes target ownership an explicit binding relation, splits the planes by enforcement owner, and wires LLM operational policy into the validate snapshot.
