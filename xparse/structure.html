系統概覽

Xparse 是什麼，以及各服務如何協作

Xparse 是一個生產級 AI 推論 API 平台，介於你的應用程式與 LLM 供應商（OpenAI、Azure OpenAI、自建 vLLM）之間。它統一處理 API 金鑰驗證、政策決策、多模型路由、串流輸出、審計日誌、GPU 節點管理與 Sandbox 執行，並對外提供完整的 OpenAI 相容 API 介面。

四大平面架構

🌐 Runtime Plane（執行平面）

bustream（Gateway :8000）—— 所有 LLM 推論請求的入口。負責 API 金鑰驗證、政策評估、准入控制、多後端路由、SSE 串流協調及審計事件發射。另包含 xparse_routing（進程內路由決策函式庫）與 xparse_resource_manager（共享端點容量佇列）。

🔐 Governance Plane（治理平面）

xparse_iam（:8010）—— 身分驗證、授權與組態的控制平面。管理 Tenant、Application、Group、API Key、Policy Bundle、Provider Credential 與 OIDC SSO。Console App（:3000）是此平面的前端管理界面。

🚀 Agent Platform Plane（代理平台平面）

xparse_fleet（:8090）負責 GPU 節點的編排排程。xparse_node_mgr（:8080）作為節點代理（agentd）運行於各 GPU 節點，管理 vLLM 容器、Sandbox 與 Agent App。xparse_container_platform 是供 node_mgr 呼叫的容器生命週期函式庫。xparse_scheduler（:8030）負責工作負載放置決策。

📊 Audit & Observability（審計與可觀測性）

xparse_audit（:8001）是雙重角色的審計系統：嵌入 Gateway/IAM 的 Python SDK（非阻塞事件寫入至 JSONL），以及供 Console 查詢事件、統計報表、產製法律證據包的 REST API。與 Grafana Tempo 整合提供分散式追蹤。

關鍵請求路徑

Client → bustream:8000 → IAM 驗證 → Policy/Admission 決策 → xparse_routing → StreamingManagerV3 → LLM Provider → Audit/Metrics → SSE 回傳 Client

失敗模式彙整

連線方向失敗時行為
Gateway → IAM 驗證每次請求出向Fail-fast → HTTP 401/500 回傳用戶端
Gateway → ResourceManager每次推論出向Fail-open → 跳過 Layer 2，記錄 RESOURCE_QUEUE_DEGRADED
Gateway → NeMo Guardrails每次請求出向Fail-CLOSED → HTTP 503（INV-139-4，絕不靜默放行）
Gateway → LLM 供應商推論時出向CircuitBreaker → RetryableWorker → HTTP 503
Gateway → Audit（OTel）背景非同步Fail-open → 事件靜默丟棄
IAM → Scheduler部署時出向Fail-fast → HTTP 503 硬失敗（ADR-121）
IAM → Fleet查詢端點時出向Fail-open → 回傳空 instance 清單
Fleet → IAM心跳出向Fail-open → 記錄 warning，下個週期重試
NodeMgr → IAM Skill Mounts工作負載建立時Fail-open → 回傳空 dict（INV-101-23）
Scheduler → Fleet 部署放置時出向Fire-and-forget → 記錄 warning，放置保持 PENDING
RM → Audit SDK進程內背景Fail-soft → 例外被吞掉（ADR-010）

服務詳細說明

每個服務的職責、功能說明與通訊對象

執行平面
bustream — Gateway
:8000 · HTTP/1.1 + SSE · FastAPI + Uvicorn
整個 Xparse 平台的 LLM 請求協調器。所有推論請求皆流經此處：API 金鑰驗證、政策評估、准入控制、多後端路由（direct 或 twin 模式）、SSE 串流協調、Guardrail 強制執行、語意快取，以及審計事件發射。對外提供 OpenAI 相容 API。
通訊對象：
→xparse_iam — 每次請求驗證 API Key（HTTP，TTL 快取 30s）
→LLM 供應商 — OpenAI / Azure OpenAI / vLLM（HTTPS/SSE）
→xparse_resource_manager — 取得/釋放端點 Lease（可選）
→xparse_fleet — 每 30s 輪詢模型 Profile（背景）
→NeMo Guardrails sidecar — 輸入/輸出安全檢查（Fail-closed）
→Grafana Tempo — OTel 審計 Span（非同步，Fail-open）
→Redis — Token 配額影子計數（可選，Fail-open）
↔xparse_routing — 進程內路由決策（SQLite DB）
治理平面
xparse_iam — 身分與存取管理
:8010 · HTTP/REST · Django + Django Ninja
治理與控制平面的核心。管理 Tenant、API Key、Application、Group、Provider Credential（加密儲存）、Policy Bundle/Binding、OIDC SSO 以及模型 Catalog。提供供 Gateway 使用的 API Key 驗證 + 憑證解密內部端點（最關鍵熱路徑），以及供 Scheduler 查詢資源配額的端點。
通訊對象：
→Keycloak — 取得 JWKS 驗證 OIDC Token（GET，TTL 1hr）
→xparse_scheduler — 觸發容器放置（POST，失敗即 503）
→xparse_fleet — 查詢 App Instance 端點（GET，Fail-open）
←Gateway — 驗證 API Key 並解密 Provider Credential
←Scheduler — 查詢群組配額、節點分配、資源需求
←Console App — 完整 CRUD 管理介面
容量平面
xparse_resource_manager
:8020 · HTTP/1.1 REST · FastAPI + Uvicorn · PyArmor
管理共享 LLM 推論端點的並發 Slot 分配。Gateway 每次推論前必須先 acquire 一個 Lease，推論結束後 release。採用帶優先權的非同步佇列與 TTL 自動回收機制，防止單一端點被超量並發壓垮。透過 xparse_audit SDK 發射審計事件。
通訊對象：
←bustream Gateway — acquire/release Endpoint Lease（HTTP 長輪詢）
→xparse_audit — 審計事件透過 SDK（Fail-soft）
代理平台
xparse_fleet — Fleet 控制平面
:8090 · HTTP/REST · FastAPI + Uvicorn
所有 GPU 節點的編排控制平面。維護節點狀態機（REGISTERED→ACTIVE），透過心跳 ACK 下發遠端命令，協調 Agent App 部署（含 Port 分配），管理模型部署，並將模型 Catalog 同步至 IAM。同時將節點回報的部署進度事件轉發給 IAM。
通訊對象：
→xparse_iam — Auth 驗證、Catalog 同步、事件轉發
→xparse_node_mgr — 服務代理呼叫（node_proxy.py）
→xparse_scheduler — 容量報告中繼（Fail-open）
←xparse_node_mgr — 每 30s 心跳
←Console App — Fleet 狀態與節點管理
←bustream — 每 30s 輪詢模型 Profile
代理平台
xparse_node_mgr — 節點代理
:8080 · HTTP/REST · FastAPI + Uvicorn（agentd）
每台 GPU 節點上的執行層代理。定期向 Fleet 發送心跳（攜帶服務狀態、GPU 指標與命令結果），執行心跳 ACK 中帶回的遠端命令（部署工作負載、建立 Sandbox、上線 Agent App），管理 vLLM 容器生命週期，處理模型下載，以及執行節點驗證測試。
通訊對象：
→xparse_fleet — 每 30s 心跳 POST（Fail-open）
→xparse_iam — Skill 掛載計畫查詢（Fail-open）
→Docker Engine — 容器生命週期（aiodocker + docker SDK）
→HuggingFace Hub — 模型 snapshot_download（HTTPS）
↔xparse_container_platform — 進程內容器 Use Case 呼叫
代理平台
xparse_scheduler — 放置排程器
:8030 · HTTP/REST · FastAPI + Uvicorn
三階段工作負載放置排程器：(1) 從 IAM 查詢資源需求，(2) 配額驗證，(3) 透過 MostRemainingStrategy 選擇節點。部署命令以 Fire-and-forget 方式下發至 Fleet。放置記錄在節點確認執行後從 PENDING 轉為 ACTIVE。
通訊對象：
→xparse_iam — 群組配額、節點分配、資源需求（Fail-fast）
→xparse_fleet — 部署應用（POST，Fire-and-forget）
←xparse_fleet — 容量心跳報告（POST /nodes/{id}/report）
←xparse_iam — 觸發放置（POST /scheduler/placements）
審計與可觀測性
xparse_audit — 審計服務
:8001 · HTTP/REST · FastAPI + Uvicorn（SDK + API）
雙重角色系統：(1) 嵌入 Gateway 與 IAM 的 Python SDK，透過有界佇列 → AsyncSinkWriter → JSONL 檔案進行非阻塞事件寫入；(2) 供 Console 查詢事件、統計報表、管理證據包（含 SHA-256 完整性的 ZIP）及透過 Grafana Tempo Span 計算每用戶使用量的 REST API。
通訊對象：
→Grafana Tempo — 關聯查詢（HTTP GET，Fail-open）
←Console App — 查詢事件、統計、證據包（REST）
←bustream（SDK）— 審計事件透過 BoundedBuffer 寫入
←xparse_iam（SDK）— 身分驗證審計事件寫入
←xparse_resource_manager（SDK）— 容量審計事件寫入
進程內函式庫
xparse_routing
無 HTTP 埠 · Python package · SQLite/PostgreSQL
bustream 專用的進程內路由決策函式庫。給定 RequestContext 與 ModelInfo 清單，套用五種路由策略之一（none/direct、smart_routing/twin、cost_first、energy_first、health_aware），回傳 ExecutionPlan。決策日誌以 Fire-and-forget 方式寫入 DB。
使用方：
←bustream Gateway — 每次請求呼叫 Resolver.resolve()
路由策略：
•none → direct（使用 models[0]）
•smart_routing → 複雜度分數 → direct 或 twin
•cost_first → 最低費用模型（附 viability guard）
•energy_first → 最低 joules/token（附 circuit breaker）
•health_aware → 健康分數加權的 twin 路由
進程內函式庫
xparse_container_platform
無 HTTP 埠 · Python package · Clean Architecture
xparse_node_mgr 使用的容器生命週期管理函式庫（六邊形架構）。提供 10 個 Use Case：CreateSandbox、StartSandbox、StopSandbox、DestroySandbox、ExecInSandbox、GetSandboxStatus、ListSandboxes、CreateNetwork、RemoveNetwork、ListNetworks。強制執行無特權容器原則（ADR-103）。支援可選的 nsjail 逐次執行隔離。
使用方：
←xparse_node_mgr — sandbox_runtime 單例
基礎設施：
→Docker Engine — aiodocker 非同步 API（Unix Socket）
→nsjail binary — subprocess 執行隔離（可選）

核心 API（SPEC-086 §4）

方法路徑用途
POST/resource/endpoints/{endpoint_id}/acquire向指定端點申請一個容量 Slot（Lease）。無空位時進入優先佇列等待。回傳 lease_id + ttl_sec。參數：app_id、tenant_id、request_id、priority（0–10+）、timeout_ms。
POST/resource/endpoints/{endpoint_id}/release依 lease_id 釋放持有的 Lease，觸發佇列下一位晉升。具備冪等保護（已釋放時回傳 409）。
GET/resource/endpoints/{endpoint_id}/status查詢端點即時 Slot 使用量：max_concurrent、active_leases、available_slots、queue_depth。

管理 API（SPEC-086 §5）

方法路徑用途

DEL/resource/endpoints/{endpoint_id}刪除端點組態。若仍有 Active Lease 則拒絕（409）。
