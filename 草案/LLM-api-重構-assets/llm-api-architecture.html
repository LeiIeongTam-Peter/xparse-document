LLM API 面重整架構

chat、messages、responses、embeddings、audio，以及之後的 images、MCP、A2A，格式都不同，但都要過同一套認證、政策、預算、稽核與記帳。這份設計建立在已核定的 ADR-494（共用 pipeline）與 ADR-492（跨面 conformance）之上。

  • 不拆 service。一個 gateway owner、一份治理核心、每個面一個 adapter。PRD-302 下另開一個 app 就不能共用治理程式碼。
  • 要修的是「預設跳過」。五家參考平台和我們的 run_pre_dispatch 都一樣：不認得的面就跳過，請求照樣放行。
  • 改成一張不能留白的「面 × stage」處置表。CI 從真路由導出面的清單，再檢查每格都填了、實際跑的和宣告的一致。

草案 §5

MCP／A2A 放哪

「MCP」在 roadmap 上有三種不同的意思，放的位置也不同。

共用(b) MCP gateway 與 A2A

  • 認證（IAM validate）、請求欄位去向、policy actions
  • 預算閘、admission／並發
  • 稽核生命週期、terminal 與記帳（單位：工具呼叫次數、任務數）
  • 面登記表、處置表、conformance

不共用各自的執行家族

  • 定址、routing、semantic cache（沒有模型）
  • 串流引擎
  • session 狀態（MCP session id、A2A task id）
  • 只屬工具的 stage：上游 server allowlist、呼叫頻率（推論面宣告不適用）

待定Q7

  • input／output rail 套在工具參數與結果上（LiteLLM 有做）
  • Policy Kernel 的資料邊界套在上游 MCP server 的位置
草案 §7

防回歸：漏接怎麼變紅

G1、G2、G5 是純 stdlib 的靜態檢查；G4 沿用現有的 gateway owner suite。每個 gate 都要先看它對植入的回歸變紅過才算數。G4 是關鍵：沒有執行期軌跡，處置表只是另一份宣告。

#機制鎖什麼對應
G1面登記表是唯一來源路由、conformance fixture、請求欄位 gate、terminal 鎖都從同一張表導出，不再有手寫的面清單S1S3
G2處置窮舉 gate每個「已登記面 × stage」恰好一個處置；強制 stage 不得不適用；不適用附文件編號、缺口附 #issueS2S3
G3路由覆蓋 gate從真 app 列舉路由：會執行的 route 必須經過 run_pre_dispatch，否則要歸類為非執行並附理由S3
G4conformance＋執行期軌跡每支測試跑所有已登記的面；實際跑到的 stage 必須等於宣告的處置S3
G5單一 terminal只有 terminal.py emit 三種終端事件；每個家族都以 settle_* 結束S2
G6執行期 fail-closed未登記的面、缺處置 → 拒絕＋稽核（最後一道防線）S3
G7usage 解析窮舉每個 usage_unit 都有解析函式；不認得的終端形狀要紅，不能算成 0S2
草案 §6

遷移切片

每片都可以獨立 merge，對 client 的行為不變；標「行為變更」的片各自一個 PR、各自宣告。先讓漏接會紅，再把新的面搬進來。

開工條件：等 /v1/responses 第二輪（W1–W16）部署到 rel 並重跑 responses_gap_probe.py 之後再開 M1。M1–M5 會動到同一批檔案。

讓漏接會紅M0–M5

  1. M0ADR-494 Amendment A、ADR-492 Amendment、SPEC-308／306 修訂
  2. M1面登記表；adapter 用精確路徑查面；未登記的面 fail-closed＋稽核
  3. M2處置表取代 Stage.surfaces（三面照今天的行為填）；adapter 改 Protocol；messages 拆出來
  4. M3conformance 從登記表導出；「事件 × 面」範圍；執行期軌跡；保留第二輪的 fake provider 形狀
  5. M4路由 gate；embeddings／audio 暫列 legacy_unpiped，名單只能縮小
  6. M5terminal 唯一化：STARTED 收成一處、非串流 FAILED 走 settle_failed（附中性證明）

搬進來M6a–M7

  1. M6a修 embeddings 失敗時 FAILED＋COMPLETED 都發（讀碼確認）行為變更
  2. M6embeddings adapter＋unary 家族；沒接的 stage 先宣告缺口，所以行為不變
  3. M7speech、transcriptions 同 M6

補缺口M8–M9

  1. M8…一個缺口一個 PR：policy_actions → request_fields → addressing → policy_kernel → endpoint_lease → input rail → transcription output rail各自宣告
  2. M9count_tokens 登記成面或歸類為非執行（Q6）
  3. 之後MCP gateway（先寫 PRD／ADR）；A2A（先選標準）
草案 §2.4 · 附錄 A

外部對照

五家都有某種共用 pipeline，漏洞全出在「功能內依面分流，遇到沒處理的面就預設跳過」。手刻流程的面漏得最多，正是我們 embeddings／audio 的現況。

平台共用的部分漏在哪MCP／A2A
LiteLLM共用 base_process_llm_request；guardrail 依 call_type 配 adapter沒 adapter 的 call_type 直接 return data（unified_guardrail.py:222-226）MCP＋A2A 都有，同 pipeline
Bifrost一個 union 型別＋一條 plugin pipeline（含串流）治理 plugin 的 token 計數 switch 漏 image／rerank／OCR／video（governance/main.go:1661-1683）MCP 同 pipeline、另一組 hook
Portkey OSS一條 tryPost；每個面只是一個 fn 字串shouldSkipHook 只認 4 種，Responses／圖片／音訊的 guardrail 靜默跳過（hooks/index.ts:449-464）沒有
One-APIauth、選 channel 在 middleware計費在 text／image／audio 各寫一份；proxy 不計費（proxy.go:17-41）沒有
vLLM共用 BaseServing；Messages 是 chat 的 adapterauth 只看路徑前綴，/tokenize、/score、/rerank 沒保護（authenticate.py:11）MCP 只接給 Responses
