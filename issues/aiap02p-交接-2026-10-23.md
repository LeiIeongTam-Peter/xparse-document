## 一、owner 指定要修的四件事

### #1、#3：`/v1/responses` 全部 500，Codex 不能用（#7272）

- **現象**（aiap02p，10-22）：所有模型的 `/v1/responses` 都回 500 `Policy evaluation failed`，chat 正常。Codex 會顯示「high demand」，重試 5 次後放棄。
- **很可能的原因**：
  - gateway 沒有 `XPARSE_BOOTSTRAP_ADMIN_KEY`。
  - `/v1/responses` 的 routing stage 每個請求都要建一個 `ResponsesBindingClient`，沒有這個 key 就拋例外，被包成通用的 500。
  - 本地拿掉這個變數，結果跟 aiap02p 一模一樣：chat 200、responses 500。
- **機器為什麼會缺這個變數**：
  - compose 的 gateway 只從 `.env` 拿環境變數，放在 `envs/secrets.env` 的話 gateway 收不到。
  - helm chart 的 gateway pod 完全沒有這個變數。
  - **owner 決定（10-23）**：不改部署設定（compose、chart），到機器上補。
- **已經做的**：#7259（SPEC-308 SR-33）讓這個 500 留下紀錄，回應本身不變。
  - 寫一筆 `REQUEST_REJECTED`，帶 stage、入口、例外型別；
  - ERROR log 帶 traceback；
  - counter `xparse_gateway_stage_unexpected_errors_total{surface, stage}`。
- **接手要做**：
  1. 請 Dallen 在 aiap02p 跑以下兩個指令。gateway 容器名稱以那台機器為準，runbook 寫的是 `xparse-scr`。
     - `docker exec xparse-scr sh -c 'env | grep -c ^XPARSE_BOOTSTRAP_ADMIN_KEY='`：印出 0 就是這個原因。
     - `docker logs xparse-scr 2>&1 | grep -m3 'Policy evaluation error'`：舊版會印出例外訊息，看到 `ResponsesBindingClient requires XPARSE_BOOTSTRAP_ADMIN_KEY` 就確定。
  2. 確定之後，在那台的 gateway `.env` 補上這個變數，然後重啟 gateway。
  3. **驗收**：
     - `/v1/responses` 每個模型都回 200。
     - Codex 用 `peter_app` 跑「建立 sum.py → 執行 → 回報 5050」能完成。本地 Codex 0.163.0 大約 4 秒。
  4. 如果不是這個原因：升版後（含 #7259），用 `X-Request-Id` 在 audit 查那筆 `REQUEST_REJECTED`，看 `stage` 和例外型別。
- **留下的風險**：新的安裝如果把 key 放在 `envs/secrets.env`，或用 helm 部署，會再遇到一樣的 500。
- **可選，要 owner 決定**：還有一個不動部署設定的做法：gateway 啟動時就檢查這個變數，缺少時在 log 和 readiness 明講，不要等到每個 `/v1/responses` 才 500（ADR-093 #4）。目前沒有人提過，也沒有做。

### AU-1：平台管理員選 All tenants 時，9 個指標整個消失，畫面顯示錯誤的 0

- **證據**：本地 audit API `/dashboard/summary`，跟 Console 一樣不帶 `surface_id`：

  | 指標 | tenant_admin | system_admin（All tenants） |
  |---|---|---|
  | request.count／error.rate／latency | 681／16.3%／… | 相同 |

- **原因**（Xparse-Audit）：
  - `seed_catalog.py`：capacity、risk_posture、governance_activity、reliability 四個 surface 的 `allowed_scopes` 沒有 `global`。
  - `routers/dashboard.py:1074-1082`：請求沒帶 `surface_id` 時，不支援這個 scope 的 surface 會被默默拿掉，照樣回 200；只有帶 `surface_id` 時才回 403。前端分不出「沒有資料」和「被拿掉」，就畫成 0。
  - 同一類 bug 在 Xparse-Audit #111（2026-08-13）修過，但當時只替 `dashboard.traffic` 加了 `global`。

  - 平台管理員該不該看到跨 tenant 的 policy／治理數字，是產品決定。但不管怎麼決定，畫面都不該顯示 0。
- **驗收**：
  - system_admin 選 All tenants 時，上面這些指標等於各 tenant 的加總。
  - TC-DASH-014 加一項跨角色檢查（見 DB-5）。
- **注意**：
  - 改的是 Audit repo，合併後要在 xparse 推進 `3rd/xparse_audit` gitlink。

### AU-2：client 帶非 UUID 的 `x-request-id` 時，那筆事件的 OTel span 送不出去

10-23 發現，issue #7273。

- 拒絕路徑會沿用 client 帶來的 `x-request-id`。`otel.py:267` 的 `_derive_trace_id` 直接用 `int(..., 16)` 轉換，遇到非 16 進位的字串就拋例外，那筆 span 不會送出。
- **影響**：OTel（Tempo）那條路徑少一筆。audit 服務裡的事件應該不受影響，但沒有實測。
- **修法方向**：非 UUID 的 id 改用雜湊推出 128-bit 的 trace id。

### AU-3：沒有新事件時，Dashboard 的 rollup 會被標成「過期」

10-23 發現，畫面影響還沒確認。issue #7274。

- `rollup_projector.py:487`：沒有新事件時直接 return，不更新 `computed_at`。
- 30 分鐘後（`AUDIT_DASHBOARD_STALE_SECONDS`，預設 1800 秒），`/dashboard/summary` 就回 `is_stale: true`、`reason: stale_rollups`，但 rollup 其實是最新的。
- **本地觀察**：`computed_at` 是 13:27Z，14:57Z 查詢時被標成 stale，中間沒有任何新事件。
- Console 的 time-series panel 會讀 `is_stale`。畫面會不會因此顯示「資料過期」，沒有確認。
- **修法方向**：沒有新事件時也刷新 `computed_at`。游標沒動，代表已經追上了。
