## 一、一句話結論

不是架構問題，也不主要是 IAM。Console 的前端架構本身很快（production build 切頁 51 ms）。讓人卡住、只能重新整理的，是前端自己的錯誤處理和依賴問題，IAM 只是觸發點；在本機覺得慢，主要是 webpack dev server 在編譯；部署環境的「資料等很久」才主要是 IAM 容量。

## 三、量測數據

### 3.1 一次切頁的時間花在哪（第一次進入，15 個側邊欄頁面）

| 情境 | 點擊 → 換頁（前端） | 換頁 → 資料到齊（等 API） | 合計 p50 / p90 |
|---|---|---|---|
| production build，IAM 正常 | 51 ms | 59 ms | 115 / 241 ms |
| production build，IAM 同時跑 3 條 `usage/aggregate` | 49 ms | 57 ms（p90 745 ms） | 116 / 785 ms |
| 你的 dev server :4001（webpack，pull 之後） | 1,230 ms | 126 ms | 1,359 / 2,363 ms |

- 前端自己的換頁成本在 production 固定約 50 ms，IAM 再忙也不變。
- IAM 忙的時候，只有呼叫 `usage/aggregate` 的頁面變慢：Applications 846 ms、Credentials 785 ms、LLM Proxies 728 ms。
- dev server 上約九成時間花在 webpack 編譯，等 IAM 只占約 130 ms。

### 3.2 本機 dev server 對照（冷啟動，同一支 probe）

| 設定 | 第一次進入：點擊 → 資料到齊 p50 / p90 | 重複進入 p50 / p90 | 首頁冷載入 | 首頁 + 15 頁下載的靜態資源 |
|---|---|---|---|---|
| webpack（修改前） | 1,279 / 3,561 ms | 196 / 360 ms ¹ | 6.4 s | 33.7 MB |
| Turbopack，API 仍經 route handler | 777 / 1,293 ms | （未量） | 1.4 s | 5.1 MB |
| **Turbopack，API 直接 rewrite（第 2 項）** | **520 / 835 ms** | **127 / 160 ms** | **1.4 s** | **5.1 MB** |

¹ 取自 :4001 已暖機的第二輪。

在 Turbopack 下，**每一個** Route Handler 請求都固定多約 240 ms（`/health` 240、`/api/config` 241、`/api/assistant/availability` 242 ms；webpack 下同一支只要 5 ms）。頁面和靜態檔不受影響，和 middleware、字型都無關，原因在 Next.js 內部，沒有追到。dev 模式原本所有 API 都經過 `/api/proxy` 這個 Route Handler，所以每支 API 都要多付這 240 ms。改成直接 rewrite 之後，同一支 IAM 請求從約 255 ms 降到 9–10 ms（全部 200）。

### 3.3 IAM 併發（本機）

- 同時打 12 個 `/console/capabilities`，總耗時約等於一個一個打（1.0–1.3 倍），代表這支請求在 IAM 裡無法平行。
- 另外跑 3 條 `usage/aggregate` 背景負載時，capabilities 從 83 ms 變 416 ms，3 秒內完成的請求從 37 個降到 24 個。
- IAM 的 Dockerfile 只起一個 uvicorn process、沒有 `--workers`（`apps/iam/xparse_iam/Dockerfile:70`）。部署環境還跑在 t3.medium、與背景 worker 共用（#4752、#3220、#5062）——推估情況比本機更糟，未實測。

### 3.4 故障注入：修正前 vs 修正後（Chrome，用 Playwright 攔截請求模擬 IAM 失敗）

| 情境 | 修正前（production build :3000） | 修正後（第 1 項 branch 的 dev server） |
|---|---|---|
| session 檢查回一次 503 | 跳到 `/login`；cookie 其實仍有效 | 留在 `/applications`，側邊欄 17 項都在 |
| capabilities 連續兩次 503，之後恢復 | 整頁 spinner，20 秒後仍在；只有手動重新整理能救 | 顯示「控制台暫時無法載入」，約 3 秒後**自己**打開頁面 |

## 四、根因歸納

1. **只寫了成功路徑。** 兩個 guard 都假設 IAM 一定會回答，所以「IAM 失敗一次」被當成最終結果：一個當成登出，一個停在 spinner。加上 #4752 為了保護單一 worker 的 IAM，把全站的 retry 上限設成一次——對一般頁面資料是對的，卻也套到了整個外殼都在等的這兩個請求上。之所以一直沒被抓到，是因為所有 guard 的測試都用「已經拿到資料」的 mock，沒有任何一個測試讓 IAM 失敗過。
2. **有共用狀態的套件被重複安裝。** Radix 的每個元件都釘死自己要的內部套件版本，Dialog、Select、Popover 在不同時間升級，結果 `dismissable-layer` 有三份、`focus-guards` 有兩份。這兩個套件把「疊了幾層 overlay、`<body>` 原本的 pointer-events」記在模組層級，三份就是三套互相看不見的狀態。#3405 當時用同樣的方式修過 `focus-scope`，但另外兩個沒有一起處理；之後是在 8 個檔案裡各自繞過（例如 `dropdown-menu.tsx` 預設 `modal={false}`），根因一直都在。
3. **本機開發工具鏈。** webpack dev server 每頁第一次進入要編譯 1–4 秒；dev server 跑在一天被 pull 好幾次的主 checkout 上，每次 pull 完又要重編；等待期間畫面只有側邊欄那一項變淡。另外 `globals.css` 的 `@import` 順序不合 CSS 規範、`react-resizable` 沒列在 `package.json`，這兩個小問題讓 Turbopack 一直跑不起來。
4. **後端容量。** IAM 是單一 process。Django 5.2 會讓每個請求各用一條 thread（`asgi.py:165`），所以不是「所有請求排一條 thread 依序處理」；真正的限制是 GIL：CPU 重的請求互相拖慢，輕的請求還能插隊完成。每頁都要的授權查詢和很重的聚合查詢放在同一個 process，沒有隔離。

## 五、觀點

**是不是架構問題？** 大部分不是。Next.js App Router 加 React Query 這套前端架構沒有問題：production build 切頁 51 ms、RSC 只有約 4 KB、沒有 long task，不需要重寫或換框架。真正算設計層面的只有兩點，而且都不用大改：

- **前端**：整個 Console 外殼被兩個 IAM 請求「全有或全無」地擋住，失敗時沒有恢復路徑。這次的修法只是讓失敗變成可恢復，沒有改動外殼結構。
- **後端**：IAM 把熱路徑和重查詢放在同一個 process。這要先在部署環境量，再決定是加 worker（主機要有閒置 CPU 才有用）還是把聚合查詢移出熱路徑（預先彙總或獨立的 worker 池）。

**主要是 IAM 嗎？** 不是。IAM 是觸發點，也是部署環境變慢的原因之一；但「要重新整理才好」這一整類問題的根因在前端。就算 IAM 永遠不慢，部署、重啟、網路中斷還是會發生，前端必須能自己恢復。

**前端本身的問題是什麼？** 是「韌性」，不是「速度」。前端的執行效能很好；它的弱點是只考慮成功路徑、依賴管理鬆散、等待時沒有任何回饋。

**建議變成慣例的事：**

1. 外殼層級的請求（session、capabilities 這類「整頁都在等」的讀取），一定要有一支「真元件 + 讓 fetch 失敗」的測試，不能只用已經拿到資料的 mock。這次的 `shell-guard-recovery.test.tsx` 可以當範本。
2. 判斷「產品慢不慢」之前，先用 production build 量。dev server 的數字主要反映的是開發工具，不是產品。
3. 效能量測一定要同時檢查 status code。這次我自己就踩到：見第七節第 2 點。

## 七、更正先前的說法

1. **「Turbopack 快 3.6–7.6 倍」說得太滿。** 那只算了「點擊 → 換頁」這一段。從點擊到資料到齊，第一次進入時：API 仍經 Route Handler 只快約 1.6 倍；改成直接 rewrite 後，p50 快 2.5 倍（1,279 → 520 ms）、p90 快 4.3 倍（3,561 → 835 ms）；重複進入也比 webpack 快（196 → 127 ms）。
2. **「直接 rewrite 後從 254 ms 降到 6 ms」是錯的。** 那個 6 ms 其實是一個很快就回來的 **500**：Next.js 的 rewrite 代理拒絕了自簽憑證，而我當時只量了時間、沒有看 status code。把憑證交給 Next 之後，實際數字是 9–10 ms，而且全部回 200。
3. **#4752 寫的「IAM 是單一 thread、所有請求依序排隊（FIFO）」不正確。** Django 5.2 會讓每個請求各用一條 thread；真正的限制是單一 process 只能用一顆 CPU（GIL），所以 CPU 重的請求會互相拖慢，輕的還能插隊完成。這會影響修法：加 `--workers` 只有在主機還有閒置 CPU 時才有用。

### B. 方法

- **切頁量測**：Playwright（系統的 Chrome，headless），用 API key 登入後依序點 15 個側邊欄項目，各點兩輪。記錄「點擊 → URL 改變」、RSC 請求、JS chunk、API 請求的開始時間與耗時、long task。「資料到齊」的定義是：沒有進行中的 API 請求、畫面上也沒有 spinner，並持續 800 ms。
- **dev server 對照**：每種設定都先清掉 `.next` 再冷啟動，用同一支 probe 量；Turbopack 那幾組是從 origin/main 匯出的副本或 branch 的 worktree 跑的。
- **Route Handler 成本**：每支路徑用 curl 連打 10–12 次，取中位數。
- **故障注入**：用 Playwright 的 `page.route` 攔截 `/apis/iam/auth/validate` 和 `/apis/iam/console/capabilities`，回 503。修正前後用同一種注入方式，結果可以直接比較。
- **Radix 重現**：用 esbuild 打包一個最小 React app，裝與 Console 相同的 Radix 版本，跑五種 overlay 組合，檢查 `<body>` 的 pointer-events 和一般按鈕還能不能點。
