但實測也找到 4 個問題，其中兩個在 aiap02p 會直接碰到：
1. **#19 在 aiap02p 很可能永遠不會觸發**。規則要 2 把不同的 key，而 aiap02p 的第二把「登入 key」如果是 tenant admin，就不能推論。反過來，兩把 key 送出 client 參數錯誤時，健康的模型會被所有 app 排除 5 分鐘（用真 vLLM 重現）。

4. **#24 在本地沒有生效**：主 checkout 的 audit submodule 沒有更新。

- **裁判設定錯誤**：應該回 4xx，而且沒有平台把 503 標成 `overloaded_error`。
- **#7168**：探索要改成依時間，光是「只在沒排名的模型裡抽」不夠。

## 各項細節

### #13（#7167）：指定裁判模型

**gateway 實測**（請求指名 gemma，content filter 判 input）：

| 裁判設定 | 正常請求 | 有害請求 |
|---|---|---|
| `auto`（gemma 自己判） | 503，0.1–0.2 秒（`classifier_unparseable`） | 451，8.9 秒 |
| 指定 `claude-haiku-5-5` | 200（chat、串流、messages） | 451，0.9 秒 |
| `auto` ＋ 備援 haiku | 200（備援接手） | 451，8.8 秒 |

**Console 實測**（從 worktree 在 :4002 啟動）：
- 打開指定 haiku 的 policy，按「New Version」：裁判模型顯示 `claude-haiku-5-5`，沒有被改回 Auto。
- 備援選 deepseek-flash 後存檔，IAM 存的 v2 是 `{"model": "claude-haiku-5-5", "fallback_model": "deepseek-flash"}`。
- 截圖：`console/nv-4-before-save.png`。

**問題**：
1. **選單可以選到這個 app 用不到的模型**。
   - 候選來自呼叫者自己的模型清單（`useModelPool()`），不是 policy 綁定的 app 的 pool，而且只排除停用的模型。本地 10 個選項裡有 4 個不在 `peter` 的 pool，其中 2 個是 unhealthy。
   - 實測裁判指定 pool 外的 `gpt-5.5`：正常和有害請求都回 503。
   - gateway log 寫了原因（`classifier.model='gpt-5.5' is not bound to this application`），client 看到的卻是「內容安全檢查暫時無法使用，請稍後重試」。
2. **Claude Code 會為這個 503 重試 10 次**。`/v1/messages` 把它標成 `overloaded_error`，Claude Code 重試 10 次、180 秒後才報錯。`auto` 裁判遇到 gemma 的 `classifier_unparseable` 也走同一條路。
3. **版本檢視看不到備援**。`policy-version-describe.ts` 只列出 `classifier.model`；整個 `classifier` 物件被當成已經處理過，所以 `fallback_model` 不顯示，也不會出現在「Other」。
4. **備援的提示少寫了兩種情況**。提示只說「讀不到答案或模型沒綁定」時才重試，但程式在 `classifier_timeout`、`classifier_error` 時也會重試。SPEC-223 C-223-28 的文字同樣漏寫。

**更好的修法**：
- **IAM 在寫入時擋下**：建立版本或綁定時，檢查指定的裁判和備援是否在每個目標 app 的 pool 裡，不在就回 400（或回傳 warning，讓 Console 顯示）。這比在 gateway 執行時才 fail-closed 好，也正好收掉 #13 新選單帶來的風險。
- **把設定錯誤和暫時性錯誤分開**：`classifier_model_unresolvable` 是設定錯誤，給它另一段 client 訊息（例如「這個 app 的 guardrail 設定無法使用，請聯絡管理員」），也不要在 `/v1/messages` 標成 `overloaded_error`。
- 版本檢視加一列「備援判定模型」。

### 新項目（#7169）：graceful 在 `/v1/messages` 串流

**6 個入口實測**（關鍵字 block，`block_presentation: graceful`）：全部 200，都有拒絕文字。
- chat：`finish_reason=content_filter`。
- messages（含串流）：`stop_reason=refusal`。
- responses：`status=completed`。

**真的 agent CLI**（同一個 policy；另一組改成 error 呈現對照）：

| CLI | graceful | error |
|---|---|---|
| Claude Code | 顯示組織文字 → 自動重送一次 → 報「API Error: Haiku 5.5 can't help with this. Start a new session to continue」＋ anthropic.com/legal/aup | `API Error: 451` ＋ 組織訊息，只送 1 次 |
| Codex | 組織文字當成一般回覆，回合正常結束 | 回合失敗、顯示組織訊息，不重試 |
| opencode | 先顯示文字，再報 `ContentFilterError: The response was blocked by the provider's content filter` | 451 ＋ 組織訊息，`isRetryable: false` |

- **重送**：Claude Code 2.1.309 對 `stop_reason: "refusal"` 有專門處理，把它當成 Anthropic 的安全分類器擋下，自動重送一次（可用 `CLAUDE_CODE_DISABLE_REFUSAL_RETRY` 關掉）。所以每個被擋的回合會送 2 次；如果是 classifier 擋的，就是 2 次計費的裁判呼叫和 2 筆 block audit。
- **錯誤訊息被換掉**：重送後 Claude Code 會改顯示它自己的錯誤訊息，把責任歸給 Anthropic。
- **session 沒有被鎖**：等 policy 解除後 resume 同一個 session，回 `pong`，正常。
- 這個行為符合 SPEC-213 C-213-4（Anthropic 入口要回 `refusal`）。問題在規格當初沒有用真的 Claude Code 驗證過。

**更好的修法**（屬 SPEC-213 層級，要 owner 決定）：
- **建議**：`/v1/messages` 的 graceful 擋下改回 `end_turn` 加拒絕文字，reason 放在 `xparse` 欄位或 header。Responses 已經有先例：SPEC-282 Rev.18（ADR-437 Amendment A）就是因為真的 Codex 的行為，把 graceful 從 `response.incomplete` 改成 `response.completed`。
- **或者**在文件寫明 agent 類 app（Claude Code、Codex、OpenCode）一律用 `block_presentation: error`。實測三家在 error 呈現下都正確顯示組織訊息、不重試，也不會誤指 Anthropic。
- **文件漂移**：SPEC-213 §8（約第 264 行）還寫著 Responses 的 graceful「never `response.completed`」，跟 SPEC-282 Rev.18 和現在的行為相反。

### #20（#7168）：latency 只比流量延遲

把 `peter` 暫時改成 latency，送 40 個自動路由請求（測完已改回 quality）：

| 請求 | 選到 | 訊號 | 有排名／沒排名 |
|---|---|---|---|
| 0–12 | haiku | `avg_latency_ms` 880–980 ms | 1–2 ／ 4 |
| 13、14 | deepseek、gemma | 探索 | — |
| 15–39 | deepseek 22 次、haiku 17 次 | deepseek 540–835 ms、haiku 880–930 ms（差 10% 以內時照 quality 順序） | 3 ／ 3 |

- **舊版會選 gemma**：舊版在「只有部分候選有流量」時會退回比 probe。本地 probe 的值是 gemma 33 ms、deepseek 249、haiku 409、luna 1078，所以舊版會一直選 gemma，也就是 aiap02p #20 的症狀。新版不會。
- **有 3 個模型一次都沒被選到**：gpt-6-luna 和兩個 Bedrock 模型在 40 次請求裡都沒被選到。它們沒有排名，只能靠 5% 的探索。

**問題**：
1. **沒排名的模型很難回到排名**。探索是從全部候選裡抽（`derive_index(seed, len(candidates))`），不是只從沒排名的裡抽。6 個候選時，每個沒排名的模型只分到約 0.8% 的流量，而延遲資料 600 秒就過期。
2. **整體延遲受輸出長度影響**。gemma 這次 0.16 秒就回答，它的平均值仍停在好幾秒，因為之前回答的都是長文。非串流請求只有整體延遲可用。
3. **過期後平均值不重新起算**。過期模型的第一筆新樣本只佔 10% 權重（`health_tracker.py:321`）。新規則下模型只能靠探索回到排名，這會把回來的時間拉得更長。

**更好的修法**：保留新規則，另外加三件事（對照其他平台後已修正，見「其他平台怎麼做」與建議第 6 項）：
- 探索改成依時間，不只是「只在沒排名的模型裡抽」。
- 超過 600 秒才到的樣本，直接當成新的起點。
- 排序改用 TTFT；整體時間用「TTFT ＋ 每 token 時間 × 共用的參考長度」。不要用 LiteLLM 的「總時間 ÷ completion tokens」，它會讓長回答顯得比較快。

### #19（#7170）：一直被拒的模型會被排除

把假 vLLM 掛在 `peter` 排序的第一位：

| 階段 | 做法 | 結果 |
|---|---|---|
| A | 同一把 key 送 12 次自動路由 | 12 次 400，沒有排除（只有 1 個來源） |
| B | 第二把 key 送 1 次 | 400（第 13 次被拒，來源變成 2 個） |
| C | 兩把 key 輪流送 6 次 | 全部 200，改由 haiku 回答；假 vLLM 一次都沒被打到 |
| D | 指名故障模型送 2 次 | 照樣 400 |
| R | 300 秒後兩把 key 輪流送 14 次 | 前 10 次 400，之後再次排除、改回 haiku |

- warning log 有一條（`model 00522bb5-… excluded from auto routing`），計數器 `xparse_gateway_routing_reliability_excluded_total` 是 6，決策稽核的 `reliability_exclusion_reasons` 也有紀錄。

**問題**：
1. **單一 key 永遠不觸發，而 aiap02p 很可能只有一把能推論的 key**。
   - 前一份文件說 aiap02p 剛好有兩把 key（app key 和登入 key）。
   - 本地同樣角色的登入 key 是 tenant admin，推論會被 403 擋下（`tenant_admin keys cannot be used for inference`）。
   - 如果 aiap02p 的登入 key 也是，那台機器上這條規則永遠不會觸發。要確認那把 key 能不能打 `/v1/chat/completions`。
2. **兩把 key 送錯參數，健康的模型就會被所有 app 排除**（真 vLLM 實測）。
   - 對 gemma 送 30 次 `temperature=-1`（29 次用 key A、1 次用 key B），真 vLLM 每次都回 400。
   - 之後的自動路由決策把 gemma 排除了，同一時間指名 gemma 的正常請求照樣回 200。
   - 第二把 key 只要被拒 1 次就湊滿條件。視窗以模型為單位，所以所有用 gemma 的 app 都會受影響。
3. **模型名稱打錯不歸這條規則管**。OpenAI 回 404，`passthrough_status_code` 把 404 轉成 503，走的是 failover 和健康分數。ADR-321 Amendment C 的 C-2 寫「401／403／404 照算」，其中 404 的部分跟程式不符。
4. **整個 pool 都被拒時沒有任何告警**。guard 會回傳原本的名單並標 `bypassed=True`，排除原因是空的，所以不計數、也不發 warning（`resolver.py:200`）。provider 對整個模型家族都拒絕時，正是最需要知道的時候。
5. **模型壞著的期間，每 5 分鐘要再失敗約 10 個使用者請求**（上表 R 階段）。
6. **log 只寫模型 UUID**，看不出是哪個模型。

**更好的修法**（依效益排序）：
- **觸發時先送一個確認請求**。
  - 門檻成立時，gateway 自己對該模型送一個最小的標準請求（一句話、小 `max_tokens`，走同一個 worker）。這個也被拒才排除；成功就表示是 client 的參數問題，不排除。
  - 300 秒後也用同一個確認請求決定要不要放回，不必讓使用者的請求失敗 10 次。
  - 這樣同時解決單一 key、誤判、每 5 分鐘失敗 10 次三個問題。
  - 前一份文件說「probe 重現不了 client 的參數」，但這正是要的效果：確認請求成功，就代表模型沒壞。
- **整池被拒時也計數、也發 warning**，用 label 標明這次沒有實際排除；log 加上模型名稱。
- 原本另外提了兩個替代做法，對照其他平台後都撤回（理由見「其他平台怎麼做」）：
  - 「只計算被拒 ≥3 次的 key」：沒有平台這樣做。
  - 「帶 `param` 的 400 當成 client 的錯」：aiap02p 原本的錯誤就帶 `param`。

### #28（#7165）：頁面開關與封鎖 key 的 audit

用本地的 system_admin key 實測（`t7_tenant_audit.py`；開關用 `page_tutorials_visible`，測完已改回 hidden）：

| 步驟 | HTTP | audit 事件 |
|---|---|---|
| PATCH hidden → enabled | 200 | `iam.tenant.feature_flags_updated`，`change_before` hidden、`change_after` enabled |
| PATCH enabled → enabled（沒改值） | 200 | 又一筆，前後都是 enabled |
| PATCH enabled → hidden | 200 | 一筆，enabled → hidden |
| PATCH 不存在的開關 | 422 | 沒有（正確） |
| tenant admin 改開關 | 403 | 沒有（正確） |

### 一直被拒的模型（#19）

- 沒有平台用「幾把 key」判斷。
- 會自動恢復的兩家（LiteLLM、one-api）都是 gateway 自己送測試請求，這就是「確認請求」的先例。
- **Bifrost 的「帶 `param` 就是 client 的錯」不能照搬**。aiap02p 原本的 gpt-6-luna 錯誤是 `{"type": "invalid_request_error", "param": "max_tokens", "code": "unsupported_parameter"}`（repo 裡 `test_openai_family_wire_shape.py:52` 和 #7170 自己的測試都收了這個 body）。照搬的話，#19 在它原本要處理的情況下永遠不會觸發。
- 能分辨兩種情況的是確認請求：
  - luna：`max_tokens` 是 gateway 自己加的，最小請求也會失敗，該排除。
  - gemma：`temperature=-1` 是 client 帶的，最小請求會成功，不該排除。
- 要注意的是，模型常常只壞在某一種請求形狀上。SPEC-256 的事故紀錄寫著：luna 帶工具的請求成功，不帶工具的 100% 失敗。agent 的流量多半帶工具，所以 90% 的比例可能根本達不到；確認請求用的是不帶工具的最小請求，會把它判成壞掉。
