## 各項細節

### #24：quota 擋下其實有 audit

- **更正**：gateway 擋下時會發 `audit.interim_application_quota.exhausted`（`admission_handler.py` 的 `_emit_interim_quota_exhausted`），本地 DB 有 7 筆。我 10-22 用 tenant admin key 查不到，就判斷成「沒有 audit」，這是錯的。
- **原因**：Audit 的 `audit_role.py` 只授權 TENANT_ADMIN 和 TENANT_AUDITOR 讀 `audit.budget.*`，沒有授權 `audit.interim_*`，查詢時被 `access/query.py` 濾掉。
- **修法**：兩個 tenant 角色多授權 `audit.interim_key_quota.` 和 `audit.interim_application_quota.` 兩個事件家族。用完整的家族名稱，不用 `audit.interim_` 前綴，以後新增的 interim 家族要另外決定。只看得到自己 tenant 的事件；其他角色不變。
- **規格**：SPEC-215 C-215-142 加一條 (d)，寫明哪些角色看得到預算和 quota 的拒絕事件（Rev.21）。
- **參考**：LiteLLM 和 Bifrost 都把被擋的請求寫進同一份請求紀錄，標成失敗。

### #28：頁面開關和封鎖 key 補 audit

### #13：Console 可以選裁判模型

- 規格（SPEC-223 C-223-15）定義 `auto` 就是「用這次路由到的模型」，IAM schema 也早就支援指定 `model` 和 `fallback_model`。問題在 Console 一律送 `"auto"`。
- **修法**：guardrail 表單多兩個選單，「判定模型」預設 Auto，「備援判定模型」預設不設。存的是模型名稱（`Model.model_name`），不是 uuid。只有用內建 LLM 判定的引擎（Xparse、OpenAI、Bedrock）才顯示。
- **順便修掉**：以前在 Console 編輯 policy，指定好的裁判模型會被悄悄改回 `auto`。
- 附了介面更新頁 `docs/ui-updates/2026-10-classifier-judge-model.md`。
- **參考**：LiteLLM 的 `llm_as_a_judge` 一定要另外設 `judge_model`；NeMo 要在 `models:` 裡指定裁判。沒有平台會用請求本身的模型當裁判。
- **待驗**：部署到 dev 後，把一個路由到 gemma 的 app 的裁判指定成 haiku，確認不再回 503 `classifier_unparseable`。gateway 這半邊 10-22 已在本地驗過（指定 haiku 時擋得對、放行也對）。

### 新：graceful 在 `/v1/messages` 串流回空白

- **原因**：`guardrail_response.py` 的 `graceful_refusal_chunk` 是 gateway 唯一一個不帶 `xparse` 標記的串流 chunk。`anthropic_translation.py` 轉 Anthropic 格式時只讀有 `xparse.event_type` 的 chunk，所以拒絕文字和 `content_filter` 都被丟掉，client 收到空白、`stop_reason=end_turn`。
- **影響**：輸入端的關鍵字過濾、輸入端的 classifier、排隊後才判的 classifier。輸出端擋下本來就正常。
- **修法**：拒絕 chunk 補 `done` 標記。`/v1/messages` 現在會收到文字 block 和 `stop_reason: "refusal"`。chat 的輸出只多一個 `xparse` 物件。
- 這跟 #15（文字只有英文）是兩件事，#15 沒改。

### #20：latency 有流量資料時只比實際延遲

- **原因**：一次決策只比一種訊號，取「每個候選都有」的那種。只要有一個候選的流量資料過期（超過 600 秒），整次決策就退回比 probe 延遲，而 probe 只是連線時間。SPEC-276:117 原本寫的是「probe 只在沒流量模型旁補位」，程式跟規格不一致。
- **新規則（SPEC-276 Rev.22，OBJ-L1）**：
  - 只要有任何候選有新鮮的流量延遲（首 token 或整體延遲），就只用那一種排序，probe 不參與。
  - 沒有那種訊號的候選不排名，只靠現有的 5% 探索請求被選到，累積樣本。
  - 全部都沒有流量資料時，才用 probe 排序，跟以前一樣。
  - 首 token 和整體延遲仍然不混著比。
  - 新的 audit 欄位 `decision_evidence.latency_unranked_count`。
- **我的決定**：
  - 探索比例設 0 不強制最低值。代價寫進規格：被排除在排名外的模型不會再被重新量測。
  - 先不保存延遲資料，也不拉長 600 秒。新規則下，資料過期的模型只是不排名，不會靠 probe 搶到流量。規格附上算式：要留在排名裡，大約需要 請求率 × 探索比例 × 600 ÷ 未排名模型數 ≥ 1；探索 5%、2 個未排名模型時，大約每分鐘 4 個請求。
- Console 的兩句說明（`latencyObjectiveNote`、`unprobedNoLatencyDataHint`）和探索比例的說明一起改了。
- **參考**：LiteLLM 的 `lowest_latency` 留最近 10 筆、1 小時過期，沒有樣本的部署當成 0（會先被選）。我們不學這點：閒置的模型每 10 分鐘資料過期一次，就會搶走流量。

### #19：一直被拒的模型會被排除

- **原因**：reliability 防護只看 `hard_constraint_rate`，只在「成功完成但輸出違規」時更新。provider 回 400 歸類成 `provider_client_error`：不 failover、不跳 breaker、不扣健康分數。所以一個每次都回 400 的模型，永遠不會被排除。
- **更正**：10-22 報告說 #6362 刻意不計 provider 錯誤，這不精確。#6362 改的是健康分數，不是 `hard_constraint_rate`，目的是不讓一個 client 的錯誤請求，把其他 session 綁定的模型換掉（INV-447-34）。
- **新規則（ADR-321 Amendment C、SPEC-276 Rev.23 OBJ-P1..P7）**：
  - 每個模型另外記最近 300 秒內 provider 的回應（最多 256 筆），跟健康分數和 circuit breaker 分開。
  - 5 分鐘內被拒 ≥10 次、被拒比例 ≥90%、來自 ≥2 把不同的 key，就從自動路由排除。
  - 過 300 秒自動恢復，不會主動送請求去試。如果還是壞的，每個時間窗大約會多失敗 10 個請求。
  - 直接指名這個模型的請求，照常拿到 provider 的 400。
  - 新的 Prometheus 計數器 `xparse_gateway_routing_reliability_excluded_total{endpoint, model_id, reason}`；開始排除時記一條 warning，每個模型每 300 秒最多一條。
- **我的決定**：
  - **門檻 2 把 key**：aiap02p 剛好是兩把（app key 和登入 key），3 把在那台永遠不會觸發。只有一把 key 的環境刻意不排除：分不出是模型壞了還是那個 client 送錯，請直接把模型移出 pool。
  - **先不看 provider 的錯誤碼**：參考平台裡只有 Bifrost 依 provider 錯誤碼分類，我們沒有 aiap02p 的 log 可以確認 400 帶什麼碼。等 log 回來再決定 `unsupported_parameter`、`model_not_found` 能不能放寬門檻。
  - **session 被換掉：接受**。要多把 key 都被拒才會觸發，符合 INV-447-34 的原意。
- **參考**：
  - LiteLLM 預設不把 400 算進冷卻，要每個部署自己開 `BadRequestErrorAllowedFails`；規則是同一分鐘失敗超過 50% 且至少 5 次，被動等 TTL 恢復。
  - Bifrost 依 provider 錯誤碼分「client 的錯」和「部署的錯」。
  - one-api 所有錯誤都算，會誤關正常的 channel。
